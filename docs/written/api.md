# API Documentation

This page is a **map**, not a specification. The authoritative API shape
lives in two generated artifacts that are never hand-edited:

| Surface | Artifact | How to view |
|---|---|---|
| REST | [`docs/generated/openapi.json`](generated/openapi.json) | `make start`, then open <http://127.0.0.1:3000/docs/scalar> |
| GraphQL | [`docs/generated/schema.graphql`](generated/schema.graphql) | Read the file, or open <http://127.0.0.1:3000/graphql> |

If this page and a generated artifact disagree, the artifact is right.

## Commands

```
make docs-api          # regenerate both artifacts
make docs-api-check    # fail if either is stale (also runs in CI)
```

Neither command needs Postgres or Redis running.

## REST surface

Documented in `openapi.json`:

- `GET /health`
- `GET /api/products`
- `POST /api/products`
- `GET /api/published_products`
- `PATCH /api/products/{id}`
- `POST /api/import-jobs`
- `GET /api/import-jobs`

## GraphQL surface

Documented in `schema.graphql`. Served at `POST /graphql`.

- Query: `products`
- Mutation: `productCreate`

## Not in either artifact

- `GET /products/{handle}` — the storefront product page. Returns HTML for
  a published product, 404 otherwise. It's a rendered page rather than a
  JSON API surface, so it isn't in the OpenAPI spec. See
  [architecture.md](architecture.md) for the render/cache path.
- `GET /docs/scalar` — the REST docs UI itself.

## Why REST and GraphQL are separate artifacts

They describe different protocols with incompatible type systems. OpenAPI
can't express a GraphQL schema and SDL can't express HTTP status codes,
path parameters, or content negotiation. Merging them would mean losing
information from both, so each surface is exported in its native format
and this page links to both.

## Compatibility adapter (external product import)

`fixtures/external-product.json` is sample **external input** — a payload
shaped the way an outside system (not Ahlan) represents a product. It is
not a native Ahlan fixture and not a description of any Ahlan endpoint's
request body.

```json
{
  "external_id": "ext_1001",
  "name": "Coffee Mug",
  "slug": "coffee-mug",
  "price": "25.00",
  "stock": 12,
  "is_visible": true
}
```

It exists to test `apps/api/src/compat/external_product.rs`, the adapter
that translates this shape into Ahlan's native `ProductCreateRequest` and
then goes through the exact same create path (validation, duplicate-handle
handling) that the native REST and GraphQL create endpoints already use.

⚠️ This is not a public API contract and is not presented as a clone of
any other platform's API. It's one fixture backing one internal adapter
function — see `specs/compatibility-prd.md` and `specs/compatibility-adr.md`
for why the adapter exists and why it's structured this way.

Field mapping (external → native):

| External field | Native field | Notes |
|---|---|---|
| `external_id` | *(not mapped)* | No native equivalent; ignored. Native IDs are always generated by Ahlan (UUIDv7). |
| `name` | `title` | |
| `slug` | `handle` | Passed through as-is — not normalized/reformatted, so it fails native handle validation the same way a native request with a bad handle would. |
| `price` | `price_cents` | Decimal string (`"25.00"`) parsed deterministically into integer cents — see the adapter's `parse_price_to_cents` for the exact rule. |
| `stock` | `inventory_quantity` | |
| `is_visible` | `published` | |
| *(none)* | `description` | External shape has no description field; always maps to `None`. |
